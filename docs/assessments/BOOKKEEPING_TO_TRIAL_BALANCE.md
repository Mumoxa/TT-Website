# Bookkeeping to Trial Balance assessment

**Status: Partially implemented — private draft, not approved or published.**

## Investigation and outcome

**Observed:** battery-v2 already saves and scores individual choice and workbook-cell answers, with public content projected through an allowlist. It has at most 30 scored items, six sections, and a 40/60 stored category split. The current server-enforced duration is 20 minutes. AP content and candidate flows must continue to use the same engine.

**Implemented:** an optional structured response table for a documents-mode section. Each row displays a supplied account label, a debit/credit selector and one positive amount field. Each field maps to a separate existing item; it is autosaved and scored by the existing engine. A table section can have up to 18 items, while ordinary sections retain their 12-item limit; the overall 30-item limit is unchanged. The public projection includes table labels and references but not the key, points or flags. Only table presentation changes; there is no new scoring engine or database migration. See `BATTERY_V2.md` for the authoring contract.

**Implemented in a newly reconstructed private draft:** a complete *listed-account trial balance* for one small, specified case: eight non-zero account balances, each with side and amount, plus separate debit and credit totals. The case supplies the account list, so it does not test selecting omitted accounts or handling an unknown or zero-balance account. It does not capture complete journals or ledger postings: the draft includes three selected journal fields and one selected ledger balance. Do not describe the draft as marking a complete set of books. A fuller construction task would need more scored fields, an explicit account-selection/extra-entry policy, suitable time and independent review; a larger response model and/or separate assessment would be needed to cover that without crowding out foundations and controls.

**Scoring design:** foundations 20, journal/ledger work 16, trial balance 44, controls 20. The practical total is 60, so the existing 40/60 normalisation produces the stated raw points. Side and amount are independently worth two points per row, with six points for each total. A wrong side can still earn amount credit; an incorrect account amount does not automatically penalise other entries. There is no follow-through, omitted/extra account detection or automated assertion that totals derive from entered rows. Related fields are dependent evidence, not independent demonstrations of competence. No validated cut score or job-performance claim is implied.

**Trade-off:** the trial balance gets substantially more weight than journals and ledger. This is a deliberate draft design under the current cap, not a validated job standard. Its 20-minute time limit is inherited and has not been tested for the 30-field form. A separate flag for an explicit unsafe payment choice is not a human review task. Human-rated handoff, reviewer decisions and audit revisions remain unimplemented. The amount parser accepts signed amounts and uses tolerance, not exact unsigned cents as recommended in the supplied blueprint. Timeout handling differs from its interrupted-attempt model.
